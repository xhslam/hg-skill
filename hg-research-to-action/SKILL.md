# Research-to-Action：现实问题攻坚流程

## 这个技能解决什么问题

用户给的往往是一个**模糊的目标**（"帮我搞定海外资金出入金""帮我做个理财账本""帮我研究清楚 X 怎么做"）。
默认情况下，AI 会立刻给一个看起来完整、其实是为自己省事、省 token、走捷径的方案，并倾向于把用户哄开心。
这种方案通常**没有真实信息来源、经不起证伪、执行到一半就跑偏**。

本技能强制用一套固定流程，把目标先变成"经得起检验的方案"，再变成"一步步能走完的执行清单"。

## 贯穿全程的四条铁律（每一步都适用）

1. **用户是方向的负责人，你是执行的助手。** 在大方向、价值判断、信息来源是否靠谱上，主动暴露你的设计让用户审核，不要替用户默默拍板。
2. **不许走捷径。** 你天然倾向于给"内核简单、省 token、看起来性感"的方案。本技能里反过来：宁可选**更死板、信息量更大、看起来不性感但逻辑上更精准**的路径。如果你发现自己在简化步骤、跳过找真相源、用一句"大概就这样"带过，停下来，那就是在偷懒。
3. **一切回到真相源。** "真相源"= 第二阶段沉淀下来的可验证知识库 + 第三阶段锁定的链路设计。每完成一步，都必须回到真相源核对，不许凭对话里的临场感觉往前推。
4. **锁定路径，不许中途漂移。** 人和 AI 沟通最常见的翻车是"聊着聊着就偏了"——你说"这样也行"，用户说"好"，于是原方案绕出去十万八千里。链路一旦定好就不改；要改，必须显式回到真相源、说明为什么改。

---

## 第一阶段：明确问题与边界

不要在目标还模糊时就动手。先把问题问清楚：

- 用户真正要的结果是什么？怎样算"做完了"（可验证的成功标准）？
- 硬约束有哪些（合规、预算、时间、已有资源、能动用的人/账号/工具）？
- 哪些是必须、哪些是可选、哪些明确不做？

**做法**：用追问把边界逼出来，一次问关键的几个，不要一口气抛二十个问题。把澄清后的目标和成功标准**写下来**，让用户确认后再进入下一阶段。这份"问题定义"是后面所有判断的起点。

---

## 第二阶段：多平台调研与筛选（建真相源）

目标是攒出一个**真实、客观、足以解决问题**的知识库，而不是张口就答。

- **来源配比**：靠谱的人的内容占主，关键词检索的结果占辅（录音里用的是 70% / 30%，可按场景调整）。原因：广撒网关键词检索再排序，质量远不如"先锁定靠谱的人、再看他们说了什么"。
- **先定义"什么叫靠谱"**：在开始抓内容前，先和用户一起明确"靠谱、稳定、精准的高质量内容"的判定标准（比如：有真实出处、可证伪、论文级或一线实践者、有时效性）。标准定了再去找。
- **主流社交媒体上挑博主的硬标准**（按以下条件筛选"靠谱的人"）：
  1. **公信力强**——在该领域有可被验证的权威性/口碑，不是营销号。
  2. **粉丝量在该领域相对较多**——在这个具体领域内属于头部或中上量级（注意是按领域比，不是看绝对数）。
  3. **更新比较规律**——持续产出、节奏稳定，说明是长期实践者而非蹭热点。
  4. **完整走通过全流程**——做的是端到端、从头到尾跑通的内容，而不是只讲片段、只谈概念、半途而废的。
- **怎么抓**：单篇可以直接按网址扒；要更高效，就依托"靠谱的人"的主页，把其全部内容抓下来再按日期/主题筛选。
- **视频转写时标记实操点**：在把视频转成文字的过程中，凡是博主进入到**需要实际操作**的环节（动手演示、点击/配置、关键步骤示范），在该处**加上时间戳，并截图保存**。这样后续执行阶段需要照着做时，能直接回到原视频对应秒数和画面核对，避免文字转写丢失关键的操作细节。
- **沉淀格式要严格**：抓回来的内容统一格式落档（来源、日期、可信度、与本问题的相关点、实操点的时间戳与截图引用），方便后续引用和核对。
- **实操点的存放与引用约定**（统一格式，方便执行阶段直接调用）：
  - 截图统一存到知识库目录下的 `screenshots/` 文件夹，命名带上来源与时间戳，例如 `screenshots/<博主名或来源id>_12-34.png`（`12-34` 即视频 12:34）。
  - 在转写文字和执行文档里，凡引用实操点一律写成固定格式：`[实操点 12:34 见 screenshots/<博主名>_12-34.png]`。
  - 这样任何一步要照着做时，都能凭这个标记一键回到原视频对应秒数和对应画面核对，文字、时间戳、截图三者始终对得上。

这一阶段的产物——筛选并沉淀好的知识库——就是后面所有步骤要反复核对的**真相源**。

---

## 第三阶段：锁定链路（列好就不改）

把"怎么做"拆成若干条清晰的执行链路（chain / path），每条链路对应一个相对独立的子目标。

- **每条链路都绑定真相源**：链路里的每一步，依据来自第二阶段的知识库，不许凭感觉编。
- **链路列好就冻结**：先把所有链路列全，确认后就不再随意改动。
- **每条链路只有两种结局**：走到成功，或走到失败。失败就说明这条路不对——回到真相源换一条路，而不是在原路上不断"那这样行不行"地缝补。
- **拒绝中途的"也可以"**：当出现"A 也行、B 也行"的分叉诱惑时，回到真相源判断，不要顺着对话漂走。

把链路设计也写下来，作为后续每一步反思的对照基准。

---

## 第四阶段：逐步执行，每步回到真相源反思

按链路一步步推进。**每完成一步，强制做一次反思**，回答三件事：

1. 对照真相源/链路设计，这一步走到哪了？
2. 已完成的工作和当前这一步是什么关系？有没有偏离原路径？
3. 下一步怎么继续往后推进？

把"每做完一步都必须做这个反思"作为对自己的硬性要求。这样做的意义：在上下文无法 100% 保留、注意力会稀释的前提下，靠"回到真相源"这个动作把工作流钉在正轨上，避免越走越偏。多条链路可以并行推进，但每条都各自遵守这个反思纪律。

> 长输出务必落档：执行过程中超过约 500 字的产出，先存成文件再呈现，所有版本都留着，方便后续回溯思路变迁（配合 handoff / hooks 机制使用）。

---

## 第五阶段：合成两份文档

四条链路都跑顺、确认无误后，合成交付物：

1. **架构文档**：把目标、真相源、各链路设计、关键判断合成一份完整的总览，说明整套方案为什么成立。
2. **执行文档**：从架构文档里单独摘出**一步一步的执行清单**，每步可独立照做，带着用户（或下一个 agent）一步步走完。

两份分开的原因：架构文档解释"为什么这么做"，执行文档解决"现在具体做什么"。

---

## 输出物模板

**架构文档（architecture.md）**
```
# [目标] 解决方案架构
## 1. 问题定义与成功标准      ← 来自第一阶段
## 2. 真相源说明（来源与筛选标准）  ← 来自第二阶段
## 3. 链路设计（每条链路 + 其依据 + 成功/失败判据）  ← 来自第三阶段
## 4. 关键判断与权衡
```

**执行文档（execution.md）**
```
# [目标] 分步执行清单
## 链路 A
- [ ] 步骤 A1：做什么 / 依据 / 完成判据  [实操点 12:34 见 screenshots/<博主名>_12-34.png]
- [ ] 步骤 A2：……
## 链路 B
- [ ] ……
> 每完成一步：回到真相源核对位置、关系、下一步。
```

---

## 反模式（出现以下情况立即停手纠正）

- 还没明确成功标准就开始给方案。
- 没有真相源、靠通用知识或一次性 web 搜索就下结论。
- 为了省事/省 token 简化或跳过步骤。
- 链路定好后又被对话带着随意改路、加分叉。
- 完成一步后不回到真相源，直接凭感觉往下做。
- 把长方案全堆在对话框里不落档。
